# Frontend Template Structure Audit

Audit date: 2026-04-15

## 1. Executive summary

- Overall health: strong compliance on the core rule set. The full template scan found **no inline `<style>` blocks, no inline `<script>` blocks, no inline `style=` attributes, and no inline `on*=` event handlers** in the HTML/Thymeleaf source templates under `src/main/resources/templates`.
- Main problems found: the issues are now structural rather than rule-breaking. A small number of templates and fragments are too large, some navigation/calendar markup is duplicated, and one template (`shared-views/tutorial/tutorial.html`) bypasses the shared `base.html` layout and re-imports global assets directly.
- Priority areas to fix first: `client-views/profile/profile.html`, `shared-views/calendar/day.html`, `public-views/home/public.html`, `universal-fragments/layout/navbar.html`, and the duplicated calendar drawer fragments. These are the main maintainability risks.

## 4. Fragmentation plan

- `src/main/resources/templates/client-views/profile/profile.html`: split the profile page into focused fragments such as `profile-sidebar-card`, `profile-details-panel`, `profile-settings-drawer`, `profile-subscription-drawer`, `profile-cards-drawer`, and modal fragments. This page is the largest template in the repo and mixes shell, drawers, modals, and multiple settings domains.
- `src/main/resources/templates/shared-views/calendar/day.html`: extract day hero, progress bar, week strip, tab panels, add-task modal, AI optimise modal, and the two drawers into `shared-views/calendar/fragments/*`. The current file is functionally cohesive but too large to edit safely.
- `src/main/resources/templates/public-views/home/public.html`: split the marketing page into section fragments such as hero, trust, roles, gallery, support-feedback, and final CTA. This will preserve the premium landing-page structure while making content iteration safer.
- `src/main/resources/templates/universal-fragments/layout/navbar.html`: split role-specific nav clusters into smaller fragments such as `navbar-client-links`, `navbar-trainer-links`, `navbar-gym-links`, and `navbar-admin-links`. The current fragment duplicates client navigation markup and is the clearest repeated-markup hotspot.
- `src/main/resources/templates/shared-views/calendar/fragments/schedule-drawer-month.html` and `src/main/resources/templates/shared-views/calendar/fragments/schedule-drawer-week.html`: consolidate the shared drawer shell and keep only view-specific content separate. They are nearly the same maintenance surface today.
- `src/main/resources/templates/client-views/dashboard/fragments/client-dashboard-shell.html`: partially fragment cards/sections such as welcome header, progress band, quick actions, and feed panels. The file is already a fragment, but it still behaves like a full page.
- `src/main/resources/templates/public-views/dashboard/client-dashboard-public.html`: split the hero, feature grid, comparison block, AI demo, and CTA into fragments if this page continues to evolve independently from the public home page.
- `src/main/resources/templates/trainer-views/schedule/add-entry.html`, `src/main/resources/templates/trainer-views/schedule/list.html`, and `src/main/resources/templates/trainer-views/workouts/index.html`: extract modal stacks, sidebars, and repeated action panels into local fragments once those flows stabilize. They are not urgent, but they will become harder to maintain if they keep growing.
- `src/main/resources/templates/shared-views/tutorial/tutorial.html`: do not fragment the markup yet. Instead, migrate it onto `base.html` so shared imports and shell behaviour stay consistent with the rest of the site.

## 5. Risk notes

- `src/main/resources/templates/universal-fragments/layout/navbar.html`: refactor carefully because both desktop and collapsed/mobile navigation depend on it, and the client role markup is duplicated in two places.
- `src/main/resources/templates/shared-views/calendar/day.html`: the page is heavily data-attribute-driven. Fragmenting it is safe, but any extraction should preserve `data-*` hooks used by `src/main/resources/static/js/calendar/day.js`, `day-navigation.js`, and `day-enhancements.js`.
- `src/main/resources/templates/client-views/profile/profile.html`: multiple drawers, modals, and hidden state containers sit in one file. Splitting without a naming plan could break `src/main/resources/static/js/profile/profile-page.js` and `profile-cards-page.js` selectors.
- `src/main/resources/templates/shared-views/tutorial/tutorial.html`: behaviour is already external, but the page bypasses the shared layout. Migrate its imports carefully so the tutorial keeps its minimal shell and does not accidentally inherit unwanted global chrome.
- `src/main/resources/templates/shared-views/calendar/fragments/schedule-drawer-month.html` and `src/main/resources/templates/shared-views/calendar/fragments/schedule-drawer-week.html`: a consolidation pass should verify both drawers really can share one base fragment before deduping them.
- Naming consistency needs manual review: `src/main/resources/templates/shared-views/exercise-log/ExerciseTutorial.html` uses a capitalised filename while most templates are kebab-case; `src/main/resources/static/css/components/Cards/*` also uses a capitalised directory name unlike the rest of the CSS tree. These are not breaking issues, but they add friction.
- Legacy/transition artefacts such as `src/main/resources/templates/trainer-views/schedule/builder-old.html` are inline-clean but should remain clearly marked as old paths so future cleanup does not wire new behaviour into the wrong page.

## 6. Final action plan

1. Leave CSS and JS extraction alone for now; there are no inline violations to fix.
2. Refactor `src/main/resources/templates/universal-fragments/layout/navbar.html` first to remove duplicated role-link markup while keeping `src/main/resources/static/js/core/navbar-page.js` unchanged.
3. Split `src/main/resources/templates/client-views/profile/profile.html` into sidebar, details, settings, subscription, and modal fragments with stable IDs/data attributes preserved.
4. Split `src/main/resources/templates/shared-views/calendar/day.html` into smaller fragments, starting with drawers and modal blocks, then the hero/progress/header sections.
5. Break `src/main/resources/templates/public-views/home/public.html` into section fragments so the marketing surface can evolve without one 795-line file.
6. Consolidate duplicated calendar drawer markup and review whether shared partials can cover both month and week drawers.
7. Move `src/main/resources/templates/shared-views/tutorial/tutorial.html` onto `src/main/resources/templates/base.html` so global asset loading and shell behaviour stay consistent across the application.
8. After those structural changes, run a second pass specifically for naming cleanup (`ExerciseTutorial.html`, `Cards/`) and for any templates that grow beyond ~300 lines without fragment boundaries.
